# TODF (Tasks · Owners · Deadlines · Fines)

Система за управление на задачи, срокове и автоматични глоби при неоснователно
закъснение, с известия по Telegram, Slack, Email/Gmail, WhatsApp, Viber и
Google Calendar.

Как работи накратко:

1. Администратор създава задача с ясен срок (deadline) и приоритет за
   конкретен служител. Ако е зададен и **Owner**, той също получава известие
   веднага, че е назначен като преглеждащ по тази задача.
2. Служителят получава известие веднага, и напомняния преди срока:
   `REMINDER_HOURS_BEFORE` часа преди (по подразбиране 24ч),
   `REMINDER_FINAL_HOURS_BEFORE` часа преди като последно напомняне (по
   подразбиране 4ч), и — при по-дълги задачи (срокът е на повече от
   `REMINDER_PERIODIC_HOURS` часа от създаването, по подразбиране 48ч) —
   периодично напомняне на всеки `REMINDER_PERIODIC_HOURS` часа, докато не
   влезе в 24-часовия прозорец. Всичко по всеки канал, за който служителят
   има зададени данни.
3. Ако срокът мине и задачата не е подадена за преглед, системата
   автоматично: маркира я като просрочена, начислява глоба по конфигурируемо
   правило (толеранс + базова сума + сума на ден закъснение) и уведомява
   служителя на всички налични канали.
4. Служителят не маркира сам задачата за „завършена“ — той я **подава за
   преглед** с описание какво е свършено и приложени файлове (скрийншоти,
   снимки). Назначеният **Owner** (мениджър, отговорен за проверка на тази
   задача) одобрява или отхвърля подаденото. Ако owner не е зададен, admin
   изпълнява тази роля.
5. Прегледът също има срок (`REVIEW_DUE_HOURS` след подаването) — ако
   owner-ът се бави, той самият започва да получава глоба по същия
   механизъм, докато не прегледа подаденото.
6. Задачи могат да бъдат **повтарящи се** (напр. „всеки вторник и сряда в
   17:00“) — системата генерира нова задача на всеки цикъл, без крайна
   дата, докато шаблонът не бъде деактивиран.
7. Ако закъснението е било основателно (болест, форсмажор и т.н.),
   администраторът анулира глобата с обяснение — служителят получава
   известие и за това.
8. Администраторите получават известие в собствена Telegram група (и/или
   Slack канал) при всяко ключово действие в системата — нова задача,
   подаване за преглед, одобрение, отхвърляне, начислена/анулирана глоба —
   независимо от личните им канали.

## Структура

- `server/` — Node.js/TypeScript API (Express + Prisma + SQLite), cron
  job за проверка на срокове, адаптери за всеки канал за известия.
- `web/` — React/TypeScript табло (Vite): задачи, глоби, служители, настройки.

## Първоначално стартиране

### Backend

```bash
cd server
npm install
cp .env.example .env      # виж по-долу за попълване на данните за всеки канал
npx prisma migrate deploy
npm run seed               # създава admin@example.com / ChangeMe123!
npm run dev                 # http://localhost:4000
```

### Frontend

```bash
cd web
npm install
cp .env.example .env        # VITE_API_URL сочи към backend-а
npm run dev                  # http://localhost:5173
```

Влез с `admin@example.com` / `ChangeMe123!` (задай истинска парола след
първия вход) и създай реалните служители от таб „Служители“.

## Задачи, срокове и глоби

- Всяка задача се създава от администратор с краен срок и приоритет
  (Low/Medium/High/Critical).
- Правилата за глоби („Настройки“ → „Правила за глоби“) определят:
  - **Толеранс (часове)** — период на изчакване след срока, преди да
    започне да тече глоба (напр. 2 часа буфер).
  - **Базова сума** — глобата при първо просрочие.
  - **Сума на ден** — добавя се за всеки следващ ден закъснение.
  - **Максимум** — таван на глобата за една задача.
  - Може да зададеш отделно правило за приоритет „Критичен“, за да
    санкционираш по-строго закъснения по важни задачи.
- Cron job-ът (`SCHEDULER_CRON`, по подразбиране на всеки 5 минути) проверява
  всички отворени задачи, маркира просрочените и начислява/ескалира глоби.
- Глоба, наложена автоматично или ръчно, може да бъде анулирана
  („Глоби“ → „Анулирай“) с текстово обяснение — това е механизмът за
  „основателно закъснение“.
- Admin може да **редактира** всяка задача (заглавие, описание, служител,
  owner, срок, приоритет) през бутон „Редактирай“, и да я **изтрие** през
  „Изтрий“. Изтриването е меко (soft-delete) — задачата изчезва от
  списъците, но остава в базата и се записва в „Дневник“ (виж по-долу), т.е.
  нищо не изчезва безследно.
- В „Задачи“ има два таба: **Активни** (всичко освен завършените) и
  **Завършени** — за да не пречат старите приключени задачи на прегледа на
  текущата работа.

## Дневник на действията (Audit Log)

Всяко създаване, редактиране или изтриване на задача, и всяка наложена
или анулирана глоба от администратор, се записва в „Дневник“ (само за
admin) — кой, кога, какво точно е направил, с пълен snapshot/diff при
поискване („Детайли“). Това е защитата срещу случайно или недобросъвестно
изтриване/промяна без следа.

## Owner, преглед и повтарящи се задачи

- **Owner** не е отделна системна роля — всеки потребител (включително
  admin) може да бъде зададен като owner на конкретна задача при
  създаването ѝ. Owner-ът е човекът, който проверява дали работата е
  свършена: получава известие при подаване, вижда описанието и
  прикачените файлове, и одобрява или отхвърля с бележка.
- Ако задачата няма зададен owner, admin действа като преглеждащ.
- Затова при създаване на служител („Служители“) избираш само **системна
  роля** — Администратор (вижда/променя всичко) или Служител — а не
  „мениджър“. Мениджър става всеки служител, зададен като Owner на дадена
  задача, и в резултат вижда собствените си задачи/глоби плюс глобите на
  хората, чиито задачи следи (тези, за които е Owner).
- Отхвърлена задача се връща в работа (`IN_PROGRESS`/`OVERDUE`) — глобата
  за просрочие на служителя продължава да тече от оригиналния срок, ако
  вече е минал.
- **Повтарящи се задачи** („Повтарящи се“ в менюто, само за admin):
  задаваш дни от седмицата + час, и системата създава нова задача на
  всеки цикъл, безкрайно, докато не деактивираш шаблона. Всяка генерирана
  задача минава през същите напомняния/глоби/преглед като обикновена
  задача.
- Всеки цикъл се създава **предварително**, не в деня на самия срок —
  `RECURRING_LOOKAHEAD_DAYS_WEEKLY` (по подразбиране 3) и
  `RECURRING_LOOKAHEAD_DAYS_MONTHLY` (по подразбиране 10) определят колко
  дни напред системата генерира и известява за предстоящите повторения —
  отделно за седмичните и месечните шаблони, тъй като месечна задача е
  по-лесно да се забрави за по-дълъг период и затова заслужава повече
  предизвестие от седмична. Така служителят вижда задачата и получава
  нормалното 24-часово напомняне преди срока, вместо да научава за нея едва
  в деня, в който е дължима.

## Задачи от разговор (voice-to-tasks)

Admin-само функционалност за извличане на задачи директно от аудио запис
(разговор, среща, диктовка) вместо ръчно въвеждане.

**Поток:** аудио → Whisper (транскрипция на български) → Claude (извличане
на задачи в JSON) → задачите се пазят като **чернови** → admin ги
преглежда/редактира/одобрява на екран „Чакащи одобрение“ → одобрена
чернова става истинска задача в системата (същите напомняния, глоби,
видимост като всяка ръчно създадена задача). **Нито една задача не се
създава директно като възложена — винаги минава първо през чернова.**

- **„Задачи от разговор“** (в менюто, само за admin): качи аудио файл
  (mp3/m4a/wav/webm/ogg) или го запиши направо в браузъра. Кратки записи
  (до ~10MB, настройва се с `VOICE_SYNC_MAX_BYTES`) се обработват веднага;
  по-дълги минават през фонова обработка с прогрес индикатор.
- **„Чакащи одобрение“**: черновите, групирани по запис, с точния цитат от
  транскрипта, от който произлиза всяка задача (за проверка, че AI-то е
  разбрало правилно). Редактируеми заглавие/описание/изпълнител/срок/
  приоритет, „Одобри“/„Отхвърли“ по едно или „Одобри всички“ наведнъж.
- **Кой какво върши** — направо в „Служители“ → редактирай служител →
  ново поле „Отговорности / експертиза (за разпределяне на гласови
  задачи)“. Списъкът с активни служители (с това описание) се праща на
  Claude при всяко извличане — не е отделен файл за поддържане, просто
  описанието на всеки човек в профила му. Ако задачата не назовава никого
  изрично, AI-то преценява по тези описания кой е най-подходящ; ако никое
  описание не пасва достатъчно добре, оставя я „unassigned“ и admin-ът я
  възлага ръчно на екрана за одобрение. Празно описание = по-слаб шанс
  тази задача да се предположи автоматично на този човек — не пречи на
  нищо друго.
- **Изисква** `OPENAI_API_KEY` (Whisper транскрипция) и `ANTHROPIC_API_KEY`
  (извличане на задачи) в Render environment variables — без тях
  функцията връща ясна грешка на български вместо да гърми неясно.
- **Ограничение:** Whisper API отказва файлове над 25MB — в тази версия
  няма нарязване/компресия на аудио, така че по-дълги записи (30+ мин)
  трябва да се съкратят преди качване. Бърза диктовка с един бутон
  (микрофон) все още не е изградена като отделен екран — само ръчно
  качване/запис на страница „Задачи от разговор“.
- Разходите (продължителност, приблизителна цена на Whisper, брой Claude
  токени) се пазят по запис в базата, макар и все още без обобщен изглед в
  интерфейса.

### Автоматично внасяне от Google Meet

Когато Google Meet е настроен да записва срещите в Drive, той запазва
видеото/аудиото и собствения си автоматично генериран транскрипт (Google
Doc) в определена папка. Сървърът периодично проверява тази папка и минава
всеки нов файл през същия поток transcribe → extract → чернова, без ръчно
качване.

- **Изисква** същите Google OAuth данни като Drive интеграцията:
  `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`
  (виж стъпките по-долу за получаването им). Без тях панелът за Google
  Meet на страница „Задачи от разговор“ просто показва, че не е
  конфигуриран — нищо друго не спира да работи.
- `GOOGLE_MEET_FOLDER_NAME` (по подразбиране `Meet Recordings`) — трябва
  да съвпада точно с името на папката в Drive, в която Meet записва.
- `GOOGLE_MEET_POLL_CRON` (по подразбиране на всеки 10 минути) и
  `GOOGLE_MEET_MAX_PER_POLL` (по подразбиране 5) определят колко често и
  колко нови файла максимум се обработват на един цикъл — за да не се
  изразходва наведнъж квотата на Whisper/Claude при голям бекграунд.
- Вече внесени записи не се обработват повторно (проверка по Google Drive
  file id). Ако Meet-транскриптът (Google Doc) вече съдържа текста на
  разговора, Whisper изобщо не се вика за него — само собственият текст на
  Meet отива директно към Claude за извличане на задачи.
- На панела „Google Meet“ (страница „Задачи от разговор“) се вижда дали
  интеграцията е конфигурирана, кога е последната проверка и резултатът
  ѝ, плюс бутон „Синхронизирай сега“ за проверка веднага, без да чакаш
  следващия автоматичен цикъл.

## Настройка на каналите за известия

Всеки канал е самостоятелен — активирай само тези, които ти трябват.
Статусът им се вижда в таб „Настройки“ на таблото (показва дали сървърът
има зададени данни, не дали конкретен служител е свързан).

За всеки служител в „Служители“ → „Редактирай“ въвеждаш неговия конкретен
идентификатор за канала (chat ID, телефон и т.н.) — известията отиват само
по каналите, за които служителят има зададени данни.

### Telegram

1. Отвори чат с [@BotFather](https://t.me/BotFather) в Telegram, изпрати
   `/newbot` и следвай стъпките — ще получиш токен.
2. Сложи токена в `server/.env` като `TELEGRAM_BOT_TOKEN`.
3. Всеки служител трябва да си отвори чат с бота и да изпрати `/start`.
4. За да намериш неговия `chat_id`: служителят пише на бота, после отвори
   `https://api.telegram.org/bot<TOKEN>/getUpdates` в браузър — ще видиш
   `chat":{"id": ...}` в отговора. Сложи това число в профила на служителя.

### Slack

Най-лесно — Incoming Webhook (известията отиват в един избран канал):

1. https://api.slack.com/apps → Create New App → From scratch.
2. Activate Incoming Webhooks → Add New Webhook to Workspace → избери канал.
3. Копирай URL-a в `server/.env` като `SLACK_WEBHOOK_URL`.

По избор — директни съобщения до всеки служител вместо общ канал:

1. В същото приложение добави OAuth scope `im:write`, `chat:write`,
   `users:read` и инсталирай в workspace-а.
2. Копирай Bot User OAuth Token (`xoxb-...`) в `SLACK_BOT_TOKEN`.
3. За всеки служител вземи неговия Slack Member ID (профил → „Copy member
   ID“) и го сложи в „Служители“.

### Email / Gmail

1. Включи 2-факторна автентикация на Gmail акаунта.
2. Създай „App password“: https://myaccount.google.com/apppasswords
3. Попълни в `server/.env`:
   ```
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=465
   SMTP_SECURE=true
   SMTP_USER=твоя_имейл@gmail.com
   SMTP_PASS=генерираната app password
   ```
4. Всеки служител автоматично получава известия на своя имейл (полето
   `email`, задължително при създаване на профила му).

### WhatsApp (Meta WhatsApp Cloud API)

1. https://developers.facebook.com/ → създай App → добави продукт
   „WhatsApp“.
2. От „API Setup“ вземи временен Access Token и Phone Number ID (за
   продукция — генерирай постоянен токен през System User).
3. Сложи ги в `server/.env` като `WHATSAPP_ACCESS_TOKEN` и
   `WHATSAPP_PHONE_NUMBER_ID`.
4. Всеки служител трябва първо да е писал на бизнес номера (WhatsApp
   Cloud API изисква предходен контакт/шаблон за първо съобщение извън
   24-часовия прозорец — за продукция ще трябва одобрен темплейт).
5. Въведи номера на служителя (в международен формат, без `+`, напр.
   `359888123456`) в неговия профил.

### Viber (Viber REST Bot API)

1. https://partners.viber.com/ → Create Bot Account → вземи Auth Token.
2. Сложи го в `server/.env` като `VIBER_BOT_TOKEN`.
3. Служителят трябва да намери бота (по линк/QR от Viber admin панела) и
   да натисне „старт“ поне веднъж — едва тогава Viber дава `user id`.
4. `user id`-то идва в webhook събитие при първия контакт (за пълна
   автоматизация в продукция се добавя webhook endpoint; за начало може
   да се вземе ръчно от Viber Bot admin панела → раздел „Subscribers“).
5. Сложи го в профила на служителя.

### Google Calendar

Известията тук се материализират като събитие в календара с popup
напомняния (1 час и 24 часа преди срока) — вместо съобщение, служителят
вижда блокирано събитие в графика си.

1. https://console.cloud.google.com/ → нов проект → Enable API →
   „Google Calendar API“.
2. „APIs & Services“ → „Credentials“ → Create OAuth client ID → Web
   application, с redirect URI `http://localhost:4000/api/integrations/google/callback`.
3. Копирай Client ID / Client Secret в `server/.env`.
4. Еднократно получи refresh token чрез OAuth Playground
   (https://developers.google.com/oauthplayground): настрой го да ползва
   твоя Client ID/Secret (иконата зъбно колело горе вдясно), избери scope
   `https://www.googleapis.com/auth/calendar.events`, оторизирай със
   акаунта, чийто календар ще приема събитията, и вземи refresh token от
   стъпка 2.
5. Сложи го като `GOOGLE_REFRESH_TOKEN`.
6. По избор — попълни `googleCalendarId` в профила на служителя, ако
   искаш събитията да отиват в конкретен негов календар, а не в
   „primary“.

### Admin broadcast (Telegram група / Slack канал за администраторите)

Независимо от личните канали на всеки потребител, администраторите могат
да получават всичко в обща Telegram група и/или отделен Slack канал.

**Telegram група:**
1. Добави бота (същия от `TELEGRAM_BOT_TOKEN`) в Telegram групата на
   администраторите.
2. Изпрати произволно съобщение в групата (за да „събуди“ бота), после
   отвори `https://api.telegram.org/bot<TOKEN>/getUpdates` — ще видиш
   `"chat":{"id": -100...}` с отрицателно число (груповите чатове имат
   отрицателен ID).
3. Сложи това число в `server/.env` като `ADMIN_TELEGRAM_CHAT_ID`.

**Slack канал (по избор):** създай отделен Incoming Webhook сочещ към
`#admins` (или какъвто канал искаш) по същия начин като личния Slack
webhook по-горе, и го сложи в `ADMIN_SLACK_WEBHOOK_URL`.

## Тестване на известията

В „Служители“ → бутон „Тест известие“ праща тестово съобщение на избрания
служител по всички канали, за които има зададени данни — вижда се резултат
за всеки канал (SENT/FAILED/SKIPPED и причина при грешка).

## Тестове

```bash
cd server
npm test
```

Покрива изчисляването на глобите (`fineCalculator`): толеранс, базова
сума, ескалация по дни, таван.
